# CI/CD Workflow

This document describes how code moves from a developer's machine to production in this project.

## Stack overview

| Part | Technology | Hosting |
|------|------------|---------|
| Frontend | React + Vite + Tailwind | Firebase Hosting |
| Backend | Node.js / Express | Firebase App Hosting (Cloud Run) |
| Database / Auth | Firestore, Firebase Auth | Firebase |
| AI | Anthropic Claude API | Called from the backend only |
| Code and backlog | GitHub | Repository, Issues, Projects |

## Pipeline at a glance

```
feature branch ──► Pull Request ──► CI checks ──► Review ──► Merge to main ──► Deploy
                        │                                                       │
                        └── Hosting preview URL                                 ├── Frontend → Firebase Hosting (GitHub Action)
                                                                                └── Backend  → Firebase App Hosting (auto rollout)
```

## 1. Development flow

1. Pick an issue from the GitHub backlog and assign it to yourself.
2. Create a branch from `main`:
   - `feature/<short-description>`
   - `fix/<short-description>`
3. Commit small, focused changes with clear messages.
4. Push the branch and open a Pull Request (PR) to `main`. Link the issue (`Closes #123`).
5. Wait for CI to pass and for a teammate to review.
6. Merge (squash merge recommended). Deployment starts automatically.

Direct pushes to `main` are not allowed.

## 2. Continuous Integration (CI)

Defined in `.github/workflows/ci.yml`. Runs on every PR and on every push to `main`.

| Job | Steps |
|-----|-------|
| `frontend` | `npm ci` → lint → test → `npm run build` |
| `backend` | `npm ci` → lint → test |

Rules:

- Both jobs must pass before a PR can be merged (enforced by branch protection).
- Tests must **not** call the real Claude API. Mock it. Real calls cost money and make tests flaky.
- Focus tests on business logic, for example law source selection (`selectRelevantSources`) and JWT auth middleware.

### Branch protection on `main`

Configured in **GitHub → Settings → Branches**:

- Require a pull request before merging
- Require at least 1 approving review
- Require status checks to pass (`frontend`, `backend`)
- Require branches to be up to date before merging
- Block force pushes

## 3. Continuous Deployment (CD)

### Frontend: Firebase Hosting

- **On PR:** a GitHub Action builds the frontend and deploys it to a temporary Firebase Hosting preview channel. The preview URL is posted as a comment on the PR.
- **On merge to `main`:** a GitHub Action builds the frontend and deploys it to the live Hosting site.
- Workflows are generated by `firebase init hosting:github` and live in `.github/workflows/`.
- Authentication uses a Firebase service account stored in GitHub Secrets (`FIREBASE_SERVICE_ACCOUNT_*`).
- Public build-time variables (`VITE_*`) are stored in GitHub **Variables**. They are not secret, because they end up in the browser bundle.

### Backend: Firebase App Hosting

- The App Hosting backend is connected to this GitHub repository.
- Live branch: `main`. Root directory: the backend folder.
- Every merge to `main` triggers a new build and rollout on Cloud Run automatically.
- Configuration is in `apphosting.yaml` (env vars, memory, scaling).
- Rollbacks can be done from the Firebase console (**App Hosting → Rollouts**).

## 4. Secrets and configuration

| Secret | Where it lives | Notes |
|--------|----------------|-------|
| Anthropic API key | Google Cloud Secret Manager | Referenced from `apphosting.yaml` via `secret:` |
| Firebase Admin credentials | Google Cloud Secret Manager | Never commit to the repo |
| Firebase Hosting deploy key | GitHub Secrets | Used only by the deploy workflow |
| `VITE_*` public config | GitHub Variables | Not secret |

Rules:

- Never commit `.env` files or keys. Keep `.env*` in `.gitignore`.
- Never expose the Anthropic API key to the frontend. All Claude calls go through the backend.
- If a secret leaks, rotate it immediately.

## 5. Local development (VS Code)

Recommended extensions:

- **GitHub Pull Requests**: review PRs and see check status in the editor
- **GitHub Actions**: view workflow runs and validate workflow YAML
- **ESLint** and **Prettier**: match the lint rules CI enforces
- **Firebase** (optional): emulator and project tooling

Before pushing, run the same checks CI runs:

```bash
# frontend
cd frontend
npm run lint && npm test && npm run build

# backend
cd backend
npm run lint && npm test
```

## 6. Releasing and rollback

- Every merge to `main` is a release. Keep `main` always deployable.
- **Frontend rollback:** Firebase console → Hosting → Release history → Rollback, or revert the commit and merge.
- **Backend rollback:** Firebase console → App Hosting → Rollouts → redeploy a previous build, or revert the commit.
- Prefer reverting the commit in Git so the repository matches what is deployed.

## 7. Future improvements

- Dependabot for npm dependency updates (`.github/dependabot.yml`)
- Separate staging App Hosting backend for testing before production
- Gate backend rollouts behind CI (disable auto-rollout and trigger via `firebase apphosting:rollouts:create` after checks pass)
- Dependency and secret scanning in CI
- Basic end-to-end smoke test against the preview URL

## Quick reference

| I want to... | Do this |
|--------------|---------|
| Ship a change | Branch → PR → CI green → review → merge |
| See my change live before merging | Open the preview URL in the PR comments |
| Add a secret for the backend | Add to Secret Manager, reference in `apphosting.yaml` |
| Undo a bad release | Revert the commit on `main`, or roll back in the Firebase console |
